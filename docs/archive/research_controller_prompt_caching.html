Research Controller Prompt Caching

A comparison of the current agent loop and a cache-friendly design for Claude Opus controller calls.

Segment rewrite logs

Retained logs show only one clear segment-generation run. It had two segments, and both reached three drafts. That is not enough evidence to say this happens often now.

Controller evidence

The audit logs show repeated Opus controller turns for the same topic, with the user prompt growing from hundreds of characters to thousands within minutes.

Likely path

Measure Anthropic usage first, then test caching on the controller loop after reshaping the prompt into append-only blocks.

Current Controller Loop

Prompt Shape Today

One large user text string is rebuilt every controller turn by _controller_payload.

S System prompt
Stable controller instructions. Too small by itself to be a strong cache target.
1 Mutable run state
ITERATIONS_COMPLETED, REMAINING_BUDGET, article count, min iterations.
2 Memory, adversary, recent Q&A
Some fields are stable, some grow, and all are inside the same text prefix.
3 Current evidence blob
The largest part, but it is rebuilt as one block after earlier mutable fields.

Why Caching Is Weak

Turn N

Cache writes a hash of the whole prefix up to the breakpoint.

→
Turn N+1

Early counters and combined text changed, so the prefix hash changes before reaching the reusable evidence.

Top-level automatic caching would probably write cache entries, but repeated reads are not guaranteed because the prompt is not arranged as a stable prefix plus changing suffix.

Cache-Friendly Controller Loop

Proposed Prompt Shape

Send Claude content blocks instead of one text blob. Put append-only evidence before mutable control state.

S System prompt
Controller rules remain stable across all turns.
A Story frame block
Topic, date, fixed budget policy, initial memory note if available.
B Seed evidence block
Initial summary/evidence. Mark cacheable when it is large enough.
C Research result blocks
Append one block per completed source-hunter answer. Put cache_control on the newest reusable block.
D Decision state suffix
Iteration number, remaining budget, instruction to return the next JSON decision. Not cached.

Expected Cache Behavior

Turn N

Writes cache through latest append-only evidence block.

→
Turn N+1

Reads prior blocks from cache, processes only the new research block and small decision suffix.

This is most useful when a story takes several controller iterations and the evidence exceeds the Opus 4.8 cacheable threshold.

Implementation Sketch

Area Current Cache-friendly change
Claude adapter claude(user_prompt: str, system_prompt: str) Accept either a plain string or a list of Anthropic content blocks.
Controller payload One formatted string from _controller_payload. New builder returns ordered blocks: story frame, seed evidence, one block per Q&A, mutable state suffix.
Cache breakpoint No cache_control. Add { "type": "ephemeral" } to the latest reusable evidence block, not to the mutable suffix.
Logging Provider/model/event/prompt text only. Record Anthropic usage: input, output, cache creation, cache reads, and estimated cost by model.
Rollout All Opus controller calls are uncached. Gate behind config, run A/B for several days, compare cache read tokens and total Anthropic spend.

Example Claude Request

The controller request would stop sending one big string. Instead it would send a list of content blocks. The reusable evidence blocks appear before the small mutable decision state.

client.messages.create(
    model="claude-opus-4-8",
    max_tokens=16000,
    thinking={"type": "adaptive"},
    extra_body={"output_config": {"effort": "high"}},
    system=[
        {
            "type": "text",
            "text": RESEARCH_CONTROLLER_PROMPT,
        }
    ],
    messages=[
        {
            "role": "user",
            "content": [
                {
                    "type": "text",
                    "text": (
                        "STORY FRAME\n"
                        "Topic: Federal Reserve June 2026 interest rate decision\n"
                        "Date: June 18, 2026\n"
                        "Minimum iterations: 2\n"
                        "Maximum iterations: 5\n"
                    ),
                },
                {
                    "type": "text",
                    "text": (
                        "INITIAL EVIDENCE\n"
                        "The seed evidence and initial summaries go here..."
                    ),
                },
                {
                    "type": "text",
                    "text": (
                        "COMPLETED RESEARCH 1\n"
                        "Question: What did the FOMC announce?\n"
                        "Answer: The source hunter found..."
                    ),
                },
                {
                    "type": "text",
                    "text": (
                        "COMPLETED RESEARCH 2\n"
                        "Question: What reasons did officials give?\n"
                        "Answer: The source hunter found..."
                    ),
                    "cache_control": {"type": "ephemeral"},
                },
                {
                    "type": "text",
                    "text": (
                        "DECISION STATE\n"
                        "Iterations completed: 2\n"
                        "Remaining budget: 3\n"
                        "Article count: 1\n\n"
                        "Return the next controller decision as JSON."
                    ),
                },
            ],
        }
    ],
)

On the next controller call, the first four blocks stay byte-for-byte identical and can be read from cache. Only a new research block and the final decision-state suffix need fresh processing.

Decision

Segment caching is not proven by the logs we have. Controller caching is more structurally promising, but only after reshaping the prompt. The first engineering step should be usage logging; the second should be a small controller-only caching experiment.
